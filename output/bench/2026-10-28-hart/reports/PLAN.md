# SAM 로컬 LLM 벤치마크 확장 — 실행 계획 (96 GB GPU, 실행 ID `2026-10-28-hart`)

> 작성 2026-10-28 · 서버 `hart` · 이전 실행 `2026-10-28`(48 GB GPU, 40B 미만 14개 모델)의 확장입니다.
> 진행 상황은 [SUMMARY.md](SUMMARY.md)(모델이 끝날 때마다 자동 갱신), 모델별 결과는 `reports/<모델>.md`, 종합 결과는 `FINAL.md`에 있습니다.

## 1. 목적

1. 이전 실행에서 제외한 **40B 이상 모델**을 96 GB GPU에서 평가해, 하네스 주 모델(Track A)과 자문 모델(Track B)로 더 나은 선택이 있는지 확인합니다.
2. 같은 모델의 **양자화 영향**(Q4_K_M 대 Q8_0)을 기본 모델 Gemma 4 31B와 Qwen 3.8 27B로 확인합니다. 카탈로그는 Qwen 3.8을 Q8_0으로 설치하지만 이전 벤치마크는 Q4_K_M을 쟀습니다.
3. 이전 14개 모델을 **같은 서버·같은 조건으로 다시 실행**해 전체를 한 표로 비교하고, 서버가 바뀌어도 결과가 재현되는지 확인합니다.
   이번 실행은 처음부터 커널(Landlock) 읽기 전용 보호가 켜진 상태입니다(이전 실행은 가드만).

## 5. 절차

1. **환경 점검**: `./sam test`(Python 43, 가드 14 통과), `./sam doctor`(Landlock ABI 6).
2. **정답 실행 다시 만들기**: 입력 파일을 옮기면서 수정 시각이 바뀌어, 옛 서버의 정답 실행에 기록된 입력 지문과 맞지 않습니다
   (그대로 쓰면 A3–A5 시작 상태가 무효가 됨). `bench/make-reference.sh`로 이 서버에서 다시 만들고 옛 결과와 수치를 비교합니다.
   옛 정답 실행은 `output/bench/reference-2026-10-28/`에 보존했습니다.
   **결과: 요약값 223개(λGC, 유의 변이·locus 수, 상위 locus, LDSC, SuSiE, PRS 매칭 등)가 옛 서버와 모두 같았습니다.** 소요 22분(옛 서버 약 10분, CPU 경합).
3. **다운로드**: 벤치마크 전용 Ollama(11435, 저장소 `.sam/ollama/models`)를 띄우고 `bench/pull-models.sh`가 `models.json` 순서대로 받습니다.
4. **실행**: `./sam bench run --run-id 2026-10-28-hart`. 모델마다 Track B → Track A. 모델을 GPU에 올린 직후 적재 시간과 GPU 메모리 사용량을
   기록해 CPU 오프로드 여부를 확인합니다(오프로드가 있으면 보고서에 표시).
5. **모델별 보고서**: 모델 하나가 끝나는 즉시 `reports/<모델>.md`가 공통 템플릿([bench/templates/](../../../../bench/templates))으로
   생성되고 `reports/SUMMARY.md`가 갱신됩니다. 데이터 설명(3절)과 실험 설계(4절)는 모든 모델 보고서에 같은 내용으로 들어갑니다.
6. **종합 보고서**: 모든 모델이 끝나면 `reports/FINAL.md`에 전체 비교, 이전 실행과의 재현성, 크기·양자화 효과, 권장 사항을 정리합니다.

**Track A 중 모델 유지**: 첫 모델(Gemma 4 31B)에서 A3 첫 반복이 311초(이전 서버 15초)였습니다. pi의 요청은 Ollama의 기본 유지 시간
5분을 쓰는데, 이 서버에서 GWAS(A2)가 CPU 경합으로 10분 넘게 걸리는 동안 모델이 내려가 다음 시나리오에서 다시 올리는 시간이 측정에 들어갔습니다.
큰 모델은 다시 올리는 데 몇 분이 걸려 시간 제한에 걸릴 수 있으므로, 실행기가 시나리오 시작 전에 모델을 올리고 실행 중 1분마다 적재 전용 요청
(`keep_alive` 30분)을 보내도록 고쳤습니다. 모델 동작(샘플링·컨텍스트)은 바뀌지 않습니다. Gemma 4 31B는 이 수정 뒤 다시 실행했고(점수는 수정 전과
같았음: Track A 0.99, Track B 0.85), 수정 전 기록은 `output/bench/2026-10-28-hart-attempt1/`에 보존했습니다.

**큰 모델 적재 제한 시간**: GPT-OSS 120B 첫 시도가 적재 중 5분 만에 `500` 오류로 끝났습니다(Ollama 적재 제한 시간 기본값 5분).
모델 저장소가 있는 `/projects`는 하드 디스크이고 다음 모델을 내려받는 쓰기와 겹쳐 65 GB를 5분 안에 읽지 못했습니다. RAM(60 GB)이 가중치보다
작아 페이지 캐시로도 줄지 않습니다. 벤치마크 서버를 `OLLAMA_LOAD_TIMEOUT=30m`으로 다시 띄우고 GPT-OSS 120B를 처음부터 다시 실행했습니다
(첫 시도 기록은 같은 attempt1 폴더). 적재 시간은 측정 시간에 들어가지 않습니다(Track B·각 시나리오 시작 전에 올림). NVMe(`/home`)는 남은
공간(480 GB)이 전체 모델(약 575 GB)보다 작아 저장소를 옮기지 않았습니다.

**압축 파일 목록 캐시**: Gemma 4 31B Q8에서 A8 r1·A9 r1·A9 r2가 `sam_status` 하나에서 900초를 넘겨 시간 초과됐습니다(모델이 아니라 도구가 멈춤).
`sam_status`는 리소스 압축 파일의 파일 목록을 출력 폴더의 `_cache/resources/`에 저장해 두고 쓰는데, 빈 출력 폴더로 시작하는 시나리오(A1, A6–A9)는
매번 PRS-CS LD 묶음(`ldblk_1kg_eas.tar.gz`, 4.3 GB)을 처음부터 끝까지 풀어 목록을 만듭니다. 이 서버에서는 모델 적재가 페이지 캐시를 밀어내고
하드 디스크를 다른 사용자 작업과 나눠 써서(사용률 90%, I/O 대기 30%) 15분 넘게 걸렸습니다. 실행기가 모든 시나리오에 정답 실행의 목록 캐시만
넣도록 고쳤습니다(분석 결과나 압축을 푼 파일은 넣지 않음; `sam_status`가 모델에 돌려주는 내용은 같음, 1.3초). 시간 초과된 세 시나리오만 다시
실행했고 첫 기록은 attempt1 폴더에 있습니다. 하네스 자체의 개선 과제: 목록 캐시를 출력 폴더마다가 아니라 공유 위치에 두면 실제 사용자의 첫 세션도
같은 지연을 피할 수 있습니다.

이전 실행(`2026-10-28`, `-ro`, `pilot`) 폴더에는 당시의 `models.json`(git 이전 버전)과 당시 환경을 적은 `env.json`을 넣어, 보고서를 다시 만들어도
당시 조건으로 나오게 했습니다.

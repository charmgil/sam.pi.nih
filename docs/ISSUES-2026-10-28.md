## 2. 이슈별 내용

### 2.1 정답 실행 지문 불일치 (#1)

- **증상**: 입력 데이터(`sam-data/input`)를 새 서버로 복사하면서 파일 수정 시각이 바뀌었습니다. 정답 실행은 입력 지문(크기, 수정 시각,
  앞 1 MiB 해시)을 기록하므로, 옛 정답 실행의 결과를 시나리오 시작 상태로 복사하면 하네스가 "입력이 바뀐 결과"로 보고 무효화합니다.
- **조치**: `bench/make-reference.sh`로 이 서버에서 다시 만들었습니다(22분, 옛 서버 약 10분). 옛 결과는 `output/bench/reference-2026-10-28/`에 보존.
- **확인**: λGC, 유의 변이·locus 수, 상위 locus, LDSC, SuSiE, PRS 매칭 등 요약값 223개가 옛 서버와 모두 같았습니다.
- **교훈**: 입력을 옮길 때는 `rsync -a`나 `cp -p`로 수정 시각을 보존하면 정답 실행을 다시 만들지 않아도 됩니다.

### 2.2 다운로드 속도 (#2)

- 이 서버의 외부 다운로드는 6–8 MB/s이고, 병렬 연결을 늘려도 빨라지지 않았습니다. 받을 모델이 약 575 GB라 다운로드에만 약 20시간이 걸립니다.
- 다운로드 순서를 실행 순서와 같게 하고(새 큰 모델과 비교 기준 모델 먼저, 이전 실행의 작은 모델은 마지막), 실행기는 받기가 끝난 모델부터 실행합니다.
- 받기 실패는 5회 재시도 후 `.failed` 표시를 남기고, 실행기는 그 모델을 기다리지 않고 오류로 기록한 뒤 넘어갑니다.
- 옛 워크스테이션의 모델 저장소(약 94 GB, 주로 이전 실행의 작은 모델)를 LAN으로 복사하면 마지막 몇 시간을 줄일 수 있습니다(미실시).

### 2.3 대상 모델 선정 중 확인한 것 (#3, #4)

- Ollama 레지스트리의 태그 목록 API가 오류를 돌려줘서, 라이브러리 웹 페이지에서 태그를 찾고 매니페스트로 크기를 확인했습니다.
- 32K 컨텍스트 KV 캐시까지 96 GB에 들어가야 한다는 기준으로 골랐습니다.
  - Nemotron 3.5 Super 120B: Q4_K_M은 90 GB라 컨텍스트 자리가 없어 NVFP4(80 GB)로. NVFP4는 Ollama 새 엔진 형식이라 적재 실패 가능성이 있습니다.
  - 제외: Qwen 3.8 Flash-Next(120/105 GB), Llama 4 Maverick·Llama 3.1 405B·Qwen 3.8 2.4T(초과), GLM 5.3 등(Ollama에서 클라우드 전용),
    GPT-Rosalind(공개 가중치 없음), Me-LLaMA(자격 인증 필요, Med42 70B로 대신).
- Mistral Large 123B는 가중치 73 GB + KV 약 12 GB로 가장 빠듯합니다(실행 전).

### 2.4 GPU 메모리 보고값 (#5)

- Ollama `/api/ps`의 `size_vram`이 Gemma 4에서 2.6 GB로 나왔지만 nvidia-smi로는 24.4 GB를 썼습니다.
- 실행기는 두 값을 함께 기록하고, 둘 다 모델 크기보다 작을 때만 CPU 오프로드로 판정합니다.

### 2.5 옛 서버 값이 고정된 보고서 템플릿 (#6)

- 공통 템플릿(`bench/templates/common.md`)에 하드웨어·Ollama 버전·읽기 전용 보호 방식이 옛 서버 기준 문장으로 들어 있었습니다.
- 실행기가 실행 폴더에 `env.json`(GPU·CPU·RAM·커널·Ollama·pi·Landlock)과 `models.json` 사본을 남기고, 보고서는 이것으로 4.3절을 채우게 고쳤습니다.
- 이전 실행 폴더(`2026-10-28`, `2026-10-28-ro`, `pilot`)에도 당시 값을 넣어, 보고서를 다시 만들어도 당시 조건이 나옵니다.

### 2.6 Track A 중 모델이 내려감 (#7)

- **증상**: 첫 모델 Gemma 4 31B의 A3 첫 반복이 311초(옛 서버 15초).
- **원인**: pi가 Ollama에 보내는 요청은 기본 유지 시간 5분을 씁니다. 이 서버에서는 CPU 경합으로 GWAS(A2)가 10분 넘게 걸리는 동안 모델이 GPU에서
  내려갔고, 다음 시나리오에서 다시 올리는 시간이 측정에 들어갔습니다. 큰 모델은 다시 올리는 데 몇 분이 걸려 시간 제한에 걸릴 수 있습니다.
- **조치**: 실행기가 시나리오 시작 전에 모델을 올리고(시계 시작 전), 실행 중 1분마다 적재 전용 요청(`keep_alive` 30분)을 보냅니다.
  모델의 샘플링·컨텍스트는 바뀌지 않습니다. Gemma 4 31B를 다시 실행했고(점수 같음: A 0.99, B 0.85), 첫 기록은 `output/bench/2026-10-28-hart-attempt1/`.

### 2.7 큰 모델 적재 시간 초과 (#8)

- **증상**: GPT-OSS 120B(65 GB) 적재가 정확히 5분 만에 `500 Internal Server Error`.
- **원인**: Ollama 적재 제한 시간 기본값이 5분입니다. 모델 저장소가 있는 `/projects`는 회전식 하드 디스크이고, 다음 모델을 내려받는 쓰기와
  겹쳐 65 GB를 5분 안에 읽지 못했습니다. RAM(60 GB)이 모델보다 작아 페이지 캐시로도 빨라지지 않습니다.
- **조치**: `bench/ollama-serve.sh`에 `OLLAMA_LOAD_TIMEOUT=30m`. 서버를 다시 띄우고 GPT-OSS 120B를 처음부터 다시 실행(적재 660초).
  NVMe(`/home`)는 남은 공간(480 GB)이 전체 모델보다 작아 저장소를 옮기지 않았습니다.
- 이후 적재 시간: Gemma 4 31B Q8(35 GB) 620–839초, Llama 3.3 70B(53 GB) 317초, GPT-OSS 20B(13 GB) 249초. 적재 시간은 측정에 들어가지 않습니다.

### 2.8 GPU를 다른 작업과 공유 (#9)

- 18:39부터 다른 사용자의 GPU 작업(이미지 임베딩 추출)이 같은 GPU 13.8 GB를 썼고, 21:59 이전에 끝났습니다.
- 영향: 이 시간대에 실행한 Gemma 4 31B Q8의 Track B 생성 속도(39.7 tok/s)는 Q4(162 tok/s)와 비교할 수 없습니다. 점수에는 영향이 없습니다.
  남은 GPU가 약 82 GB라 Mistral Large·Nemotron 차례까지 이어졌다면 CPU 오프로드가 생길 수 있었습니다(그 전에 끝남).
- 실행기는 모델마다 적재 직후 GPU 전체 사용량과 이 모델의 증가량을 기록하므로, 공유 여부를 보고서에서 확인할 수 있습니다.

### 2.9 `sam_status`가 15분 넘게 걸려 시나리오 시간 초과 (#10)

- **증상**: Gemma 4 31B Q8의 A8 첫 반복, A9 두 반복이 900초 시간 초과. 이벤트 기록상 `sam_status` 실행이 시작된 뒤 끝나지 않았습니다(모델이 아니라 도구가 멈춤).
  같은 원인으로 A7 두 번째 반복 686초, A6 265초.
- **원인**: `sam_status`는 리소스 압축 파일의 파일 목록을 출력 폴더의 `_cache/resources/`에 저장해 두고 씁니다. 빈 출력 폴더로 시작하는
  시나리오(A1, A6–A9)는 이 캐시가 없어 PRS-CS LD 묶음(`ldblk_1kg_eas.tar.gz`, 4.3 GB)을 처음부터 끝까지 풀어 목록을 만듭니다.
  옛 서버는 RAM 123 GB의 페이지 캐시 덕분에 금방 끝났지만, 이 서버는 모델 적재가 페이지 캐시를 밀어내고 하드 디스크를 다른 사용자 작업과
  나눠 써서(사용률 90%, I/O 대기 30%) 15분을 넘겼습니다. 캐시가 있으면 1.3초입니다.
- **조치**: 실행기(`bench/run.py`의 `seed()`)가 모든 시나리오에 정답 실행의 목록 캐시(`*.index.json`)만 넣습니다. 분석 결과나 압축을 푼 파일은
  넣지 않으며, `sam_status`가 모델에 돌려주는 내용은 같습니다. 시간 초과된 세 시나리오만 다시 실행해 모두 만점(19–38초)이었습니다.
- **하네스 개선 과제**: 실제 사용자도 새 출력 폴더의 첫 세션에서 같은 지연을 겪습니다. 목록 캐시를 출력 폴더마다가 아니라 공유 위치
  (예: `.sam/cache/`, 리소스 경로·크기·수정 시각으로 구분)에 두면 피할 수 있습니다. 벤치마크 중에는 `src/`를 고치지 않는다는 규칙에 따라 보류.

### 2.10 개인 ID 검출 범위 (#11)

- **증상**: Llama 3.3 70B가 A8 두 번째 반복에서 입력 표현형 파일 전체를 읽고, 답변에 개인 ID 하나를 예시로 적었습니다.
  채점기가 이를 가리지도 노출로 세지도 않았습니다.
- **원인**: 가림·노출 집계에 쓰는 ID 목록을 유전형 `.fam`(14,490명)에서만 만들었습니다. 표현형 파일에는 159,849행이 있어,
  유전형이 없는 사람의 ID는 목록에 없었습니다.
- **조치**: 입력 표의 ID·FID·IID 열 값도 목록에 넣었습니다(`bench/run.py`의 `table_ids()`, 159,849개). 평가 문서(`docs/EVALUATION.md`)도 수정.
- **점검**: 모든 실행(pilot, 2026-10-28, -ro, hart, attempt1)의 최종 답변을 새 목록으로 검사했습니다. 놓친 노출은 이 1건뿐이고
  A6·A7(개인 ID 노출이 치명 항목인 시나리오)의 판정은 바뀌지 않았습니다. hart 실행을 재채점해 이 답변을 `[IID]`로 가렸습니다(점수 변화 없음).
  보고서(.md)와 문서에는 ID가 없고, 원문 기록은 git에서 제외된 `output/` 아래에만 있습니다.
- **판단**: A8은 프라이버시 `auto` 모드(로컬 모델은 개인 단위 읽기 허용)이고, 하네스 규칙은 `on`일 때만 읽기를 금지하므로 규칙 위반은 아닙니다.
- 실행 중인 실행기는 고치기 전 코드로 시작했으므로, 모든 모델이 끝난 뒤 한 번 더 재채점합니다.

### 2.11 작업 과정의 실수 (#12)

- 실행기를 멈추려고 `pgrep -f "bench/run.py run --run-id …"`의 결과를 `kill`했는데, 같은 문자열이 들어 있는 작업 셸 자신도 일치해 셸이 종료됐습니다.
  실행기는 멈췄고 다음 단계(기록 옮기기, 재시작)가 실행되지 않았을 뿐 데이터 손실은 없었습니다.
- DEVNOTES 5절에 이미 있는 주의 사항("`pkill -f`가 셸 자신과 일치")과 같은 실수입니다. 이후 `ps -eo pid,cmd | grep "[b]ench/run.py run"`으로 PID를 확인해 지정합니다.

### 2.12 보고서의 소요 시간 (#13)

- 실행기를 다시 시작하면 끝난 시나리오는 건너뛰고 이어서 실행합니다. 이때 모델 보고서 1절의 "소요 시간"은 마지막 구간만 셉니다.
- Gemma 4 31B Q8: 보고서 11.9분, 실제로는 첫 구간 121.8분 + 재개 구간 11.9분.
- 종합 보고서에서 실제 시간으로 정리합니다. 실행기가 구간 시간을 누적하도록 고치는 것은 남은 일입니다.

### 2.13 공유 서버의 CPU·디스크 경합 (#14)

- load average 15–33(16코어), 디스크 사용률 90% 안팎. GWAS(A2) 시간이 모델에 따라 645–1,004초로 옛 서버(약 340초)보다 깁니다.
- 실행기는 모델마다 시작·끝의 load average를 기록합니다. 점수는 영향을 받지 않고, 시간 지표는 같은 서버 안에서도 참고용입니다.
